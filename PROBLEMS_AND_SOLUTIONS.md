# Problems & Solutions — Agentic Quantum Optimization Copilot

A complete record of every error, bug, and problem encountered during development,
along with what caused it and how it was fixed.

---

## 1. IBM Open Plan — Session Not Authorized (Error 1352)

**Error message:**
```
Pipeline stopped: [execution_manager] COBYLA optimisation failed:
Estimator MCP error: '400 Client Error: Bad Request for url: ...
You are not authorized to run a session when using the open plan. (error code: 1352)'
```

**What caused it:**
The original code wrapped all IBM quantum calls inside a `Session` context manager:
```python
with Session(backend=backend) as session:
    estimator = EstimatorV2(session=session)
    ...
```
IBM's Open Plan (the free tier) does not allow Sessions. Sessions are a paid feature
that reserve exclusive access to a quantum device. On the Open Plan, you must call
primitives directly without any session wrapper.

**How it was fixed:**
Removed the `with Session(...)` block entirely and called primitives directly:
```python
estimator = EstimatorV2(mode=backend)
job = estimator.run([pub])
```

**File:** `mcp_server.py`

## 2. Wrong Keyword Argument for IBM Primitives — `backend` vs `mode`

**Error message:**
```
Pipeline stopped: [execution_manager] COBYLA optimisation failed:
Estimator MCP error: EstimatorV2.__init__() got an unexpected keyword argument 'backend'
```

**What caused it:**
After removing the Session, the primitives were initialized as:
```python
estimator = EstimatorV2(backend=backend)
sampler   = SamplerV2(backend=backend)
```
IBM's `qiskit-ibm-runtime` primitives (`EstimatorV2`, `SamplerV2`) do not accept
a `backend` keyword argument. The correct keyword is `mode`.

**How it was fixed:**
```python
estimator = EstimatorV2(mode=backend)
sampler   = SamplerV2(mode=backend)
```

**File:** `mcp_server.py`

## 3. Unsupported Native Gates on IBM Hardware — `u` Gate Deprecated

**Error message:**
```
Pipeline stopped: [execution_manager] COBYLA optimisation failed:
Estimator MCP error: 'The instruction u on qubits (0,) is not supported by
the target system ibm_brisbane. The u gate is not natively supported after
March 4, 2024.'
```

**What caused it:**
The QAOA circuit generated by Qiskit used high-level gates like `u`, `rx`, `rz`
that are not natively understood by IBM quantum hardware. IBM backends only accept
their native gate set (`cx`, `rz`, `sx`, `x`). Circuits must be compiled
(transpiled) into this native set before submission. This requirement was enforced
from March 4, 2024 onwards.

**How it was fixed:**
Added `generate_preset_pass_manager` to transpile circuits before submission:
```python
from qiskit.transpiler.preset_passmanagers import generate_preset_pass_manager

pm = generate_preset_pass_manager(optimization_level=1, backend=backend)
transpiled = pm.run(circuit)
```
Applied to both the Estimator and Sampler paths in `mcp_server.py`.

**File:** `mcp_server.py`, `modules/circuit_constructor.py`

## 4. Observable Layout Mismatch After Transpilation

**What caused it:**
After transpiling the circuit with `generate_preset_pass_manager`, Qiskit remaps
logical qubits to physical qubits on the hardware. If the Hamiltonian (Ising
observable) is passed as-is, it still refers to the old logical qubit indices.
This means the expectation value is computed on the wrong qubits, producing
completely incorrect energy values — and no error is raised.

**How it was fixed:**
After transpilation, the observable must be remapped to match the new physical
qubit layout:
```python
transpiled = pm.run(circuit)
mapped_observable = observable.apply_layout(transpiled.layout)

pub = (transpiled, mapped_observable, params)
job = estimator.run([pub])
```

**File:** `mcp_server.py`

## 5. Deprecated IBM Quantum Channel Name

**What caused it:**
The `.env` file and some code paths used `IBM_QUANTUM_CHANNEL=ibm_quantum`.
This channel name was deprecated by IBM and replaced with `ibm_quantum_platform`.
Using the old name caused authentication failures.

**How it was fixed:**
Added a `_runtime_channel()` helper that normalizes the channel name:
```python
def _runtime_channel() -> str:
    channel = os.getenv("IBM_QUANTUM_CHANNEL", "ibm_quantum_platform").strip()
    if channel == "ibm_quantum":
        return "ibm_quantum_platform"
    return channel or "ibm_quantum_platform"
```

**File:** `mcp_server.py`, `modules/circuit_constructor.py`

## 6. QAOA Circuit Too Deep for IBM Hardware

**What caused it:**
QAOA circuits with a high number of `reps` (repetitions of the cost + mixer layer)
produce very deep circuits. IBM hardware has limited coherence time — circuits that
are too deep accumulate too much noise and produce meaningless results. IBM also
rejects circuits that exceed depth limits.

**How it was fixed:**
Added a loop in `circuit_constructor.py` that tries decreasing values of `reps`
until the transpiled circuit depth is ≤ 200:
```python
for reps in range(max_reps, 0, -1):
    ansatz = QAOAAnsatz(cost_operator=hamiltonian, reps=reps)
    # transpile and check depth
    if transpiled_depth <= 200:
        break
```
If no valid depth is achievable, a `RuntimeError` is raised instead of silently
submitting an oversized circuit.

**File:** `modules/circuit_constructor.py`

## 7. IBM Connection Failure — Silent Fallback to Local Simulator

**What caused it:**
The original error handler in `agents/graph.py` switched to `aer_simulator`
whenever IBM execution failed. This meant a user asking to run on IBM hardware
would silently get local simulation results — looking like IBM results but
actually being local.

**How it was fixed:**
Changed `handle_error` to preserve the requested backend and retry on the same
backend rather than silently switching. If IBM fails, an explicit error is shown
to the user rather than a misleading local result.

**File:** `agents/graph.py`, `modules/execution_manager.py`

## 8. IBM Classical Register Name — `result[0].data.meas` AttributeError

**What caused it:**
After IBM transpilation, the classical register in the circuit can be renamed
(e.g., from `meas` to `c`, `c0`, or another name depending on Qiskit version
and circuit structure). The original code hardcoded:
```python
counts_raw = result[0].data.meas.get_counts()
```
If the register was not named `meas`, this raised `AttributeError`, causing
sampling to fail and results to not appear.

**How it was fixed:**
Added `_extract_counts()` helper that tries common register names and falls back
to scanning all attributes:
```python
def _extract_counts(pub_result) -> dict[str, int]:
    data = pub_result.data
    for reg_name in ("meas", "c", "c0", "cr", "m"):
        bit_array = getattr(data, reg_name, None)
        if bit_array is not None and hasattr(bit_array, "get_counts"):
            return {k: int(v) for k, v in bit_array.get_counts().items()}
    # Fallback: scan every attribute for one with get_counts()
    for attr_name in dir(data):
        if attr_name.startswith("_"):
            continue
        attr = getattr(data, attr_name, None)
        if attr is not None and hasattr(attr, "get_counts"):
            return {k: int(v) for k, v in attr.get_counts().items()}
    raise RuntimeError("Could not find measurement register in result data")
```

**File:** `mcp_server.py`

## 9. Results Not Showing on the Dashboard After Optimization

**What caused it:**
All result rendering (sections 01–06) was placed inside `if run_btn:` in
`app.py`. In Streamlit, the entire script reruns every time the user interacts
with any widget (opens an expander, scrolls, changes a dropdown, etc.). On
each rerun, `run_btn` is `False`, so the results section never renders.

For IBM hardware jobs that take several minutes, this was especially
problematic — by the time the job finished, the user may have interacted with
the page, causing the results to vanish immediately.

**How it was fixed:**
Stored the result in `st.session_state` immediately after the pipeline
completes, and moved all result rendering outside the `if run_btn:` block:
```python
# Inside if run_btn: — save result to session state
st.session_state["_result"] = result

# Outside if run_btn: — render from session state (survives reruns)
if "_result" not in st.session_state:
    st.stop()
result = st.session_state["_result"]
# ... render all sections ...
```

**File:** `app.py`

## 10. Broken Semantic CSS Colors — Everything Was Purple

**What caused it:**
The CSS variables for status colors in `app.py` were all set to purple shades:
```css
.metric-value.green  { color: #6d28d9; }  /* This is purple, not green! */
.metric-value.amber  { color: #7c3aed; }  /* Also purple */
.metric-value.red    { color: #8b5cf6; }  /* Also purple */
```
Constraint-satisfied badges showed purple instead of green, violation badges
showed purple instead of red, and warning metrics showed purple instead of amber.

**How it was fixed:**
Replaced with correct semantic colors:
```css
.metric-value.green  { color: #059669; }  /* Emerald green */
.metric-value.amber  { color: #b45309; }  /* Amber */
.metric-value.red    { color: #dc2626; }  /* Red */
```

**File:** `app.py`

## 11. `aer_simulator` Removed from Backend Dropdown

**What caused it:**
An earlier version of `app.py` only listed IBM backends in the dropdown,
requiring an IBM token to run anything. Users without an IBM account had
no way to test the system locally.

**How it was fixed:**
Restored `aer_simulator` as the first and default option:
```python
backend_options = ["aer_simulator"] + ibm_backends
backend_name = st.selectbox("Backend", options=backend_options, index=0)
```

## 12. IBM Token Hard-Block — App Crashed Without Token

**What caused it:**
The app checked for `IBM_QUANTUM_TOKEN` at startup and raised an error if
not found, even if the user only wanted to run locally on `aer_simulator`.

**How it was fixed:**
Made the IBM token completely optional. IBM backends are only fetched if a
token exists; otherwise only `aer_simulator` appears in the dropdown:
```python
@st.cache_data(show_spinner=False)
def _ibm_backends() -> list[str]:
    token = os.getenv("IBM_QUANTUM_TOKEN", "").strip()
    if not token:
        return []   # No token → no IBM backends, no crash
    ...
```

**File:** `app.py`

## 14. f-String Backslash SyntaxError (Python 3.9)

**Error message:**
```
SyntaxError: f-string expression part cannot include a backslash
  File "app.py", line 714
      for c in candidates
```

**What caused it:**
The candidates table row used escaped quotes inside an f-string expression:
```python
f'<td>{"<span class=\'badge badge-green\'>✓</span>" if c["constraint_satisfied"] ...}'
```
Python 3.9 does not allow backslash escapes inside f-string `{}` expressions.
(This restriction was lifted in Python 3.12.)

**How it was fixed:**
Extracted the HTML strings into variables before the f-string:
```python
_ok_badge   = "<span class='badge badge-green'>✓</span>"
_fail_badge = "<span class='badge badge-red'>✗</span>"
# Then inside the f-string:
f'<td>{_ok_badge if c["constraint_satisfied"] else _fail_badge}</td>'
```

**File:** `app.py`

## 15. Streamlit Event Loop Conflict with Async MCP Client

**What caused it:**
The MCP client (`mcp_client.py`) uses `asyncio` to communicate with the MCP
server subprocess. Streamlit runs its own event loop internally. Calling
`asyncio.run()` inside a Streamlit callback raises:
```
RuntimeError: This event loop is already running.
```

**How it was fixed:**
Used a `ThreadPoolExecutor` to run the async MCP calls in a separate thread
with its own event loop, bypassing the conflict with Streamlit's loop:
```python
import concurrent.futures

def _call_mcp_tool(tool_name: str, arguments: dict) -> dict:
    with concurrent.futures.ThreadPoolExecutor(max_workers=1) as executor:
        future = executor.submit(_run_async, tool_name, arguments)
        return future.result()

def _run_async(tool_name, arguments):
    loop = asyncio.new_event_loop()
    asyncio.set_event_loop(loop)
    try:
        return loop.run_until_complete(_async_call(tool_name, arguments))
    finally:
        loop.close()
```

**File:** `tools/mcp_client.py`
